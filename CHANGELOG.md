# Change Log
All notable changes to this project will be documented in this file.

- **19_06_2026** (Version 2.0.0 Major Update):
  - **Rust Core Engine**: Completely rewrote the data processing pipeline (parsers, molecule derivation, filters, writers) in Rust via PyO3, replacing the pure Python implementation for massively increased high-throughput processing speed.
  - **Headless CLI Mode**: Introduced a new `--cli` mode to run FragHub without the graphical interface, ideal for servers and automated data pipelines. Features advanced real-time metrics (ETA, speed) and a `--quiet` flag.
  - **Recursive Directory Parsing**: Added input resolution in CLI mode to automatically scan entire folder structures and batch-process valid MS files.
  - **Backend Modernization**: Updated the FastAPI Python backend to use modern `lifespan` handlers, resolving deprecation warnings, and upgraded Pydantic schemas to v2 standards (`ConfigDict`).
  - **Agnostic Callback System**: Built a robust event bridge allowing the Rust engine to safely stream asynchronous progress logs to both the CLI terminal and the Electron/Nuxt GUI via WebSockets.
  - **Toolchain Migration**: Transitioned the entire Python environment and dependency management to `uv`, significantly speeding up setup and resolving packaging constraints with PyInstaller across OS environments.
  - **Interactive Reporting**: Developed a comprehensive HTML execution report incorporating interactive Sunburst and UpSetPlot charts that summarize dataset evolution after processing.
  - **UI/UX & Logs Polishing**: Disabled the automatic launch of Electron Developer Tools at startup, unified the application icons, and drastically cleaned/standardized all the real-time progress steps displayed during processing.
  - **Packaging Fixes**: Resolved Python multiprocessing freeze issues when packaging the Rust-RDKit bridge with PyInstaller, and updated Electron metadata.
  - **RDKit C++**: molecule derivation and exact masses are computed by RDKit C++ called directly from Rust, on all cores; RDKit Python is no longer used nor bundled.
  - **License**: FragHub is now distributed under the CeCILL 2.1 license (`LICENSE`), replacing CC BY-NC 4.0.
  - **Input files**: extensions are recognized in upper or lower case (`.MSP` files were found but silently not read), `.jsonl` files are read, and MSP files with several peaks per line (NIST format, `85 999; 86 23;`) keep all their peaks (only the first peak of each line was read). Metadata reading: `FILENAME` is the original database file name when the spectrum gives one (`FILENAME=` in MSnLib or GNPS MGF, GNPS JSON `source_file`), otherwise the input file name, and the rules that recognize a file by its name (GC `_GC` suffix, in silico libraries) always use the input file name (before, a `FILENAME` field in the spectrum silently replaced it for these rules too); an empty or `N/A` field no longer hides a filled field of the same meaning (GNPS JSON `INCHI_AUX` = `N/A` now gives way to `InChIKey_smiles`); MoNA JSON values recomputed by MoNA (`computed`) are used only when the original value is missing (the submitter's SMILES was replaced by MoNA's, without stereochemistry); new field names read: `ionization`, `ion source`, `dissociation method`, `fragmentation_method`, `InChIKey_smiles` / `InChIKey_inchi`, `Formula_smiles` / `Formula_inchi`, Spectraverse `COLLISION_ENERGY_1/2/3` (joined; fields 1 and 2 are a ramp and fields 1, 2 and 3 are steps, as described in the Spectraverse article, written `Ramp` / `Stepped`; the `eV` unit given by the article is added only for Spectraverse spectra, recognized by their `SPECTRAVERSE…` identifier and their normalized collision energy fields); JSON lists of values are read as text (MSnLib merged spectra: `collision_energy` = `[20.0, 30.0, 60.0, 40.0]` was ignored); an empty adduct is read from the end of the name when it is written there and is a known adduct (GNPS MGF: `Hectochlorin M+Na`), and removed from the name; MoNA MSP `computed` values are used as a fallback too, like in JSON; library identifiers are read when `SPECTRUMID` is missing or only a number (Spectraverse `TITLE`, MSnLib 2025 `USI`); collision energy and InChIKey written at the end of the name are removed (MS-DIAL: `Piperine; CE0; MXXW…`); two fields written on one MSP line are split (GNPS MSP `RETENTIONTIME: CCS: …`), only when the second colon is followed by a space (MassBank RIKEN `LINKS: INCHIKEY:…; CAS:…` is kept whole); peaks separated by blank lines are kept with their spectrum (MSP: a block made only of peak lines belongs to the previous spectrum, e.g. MoNA; MGF: blank lines are ignored), they were lost or read as separate spectra; an empty MGF field (`KEY=`) no longer takes the next line as its value; quotes around a SMILES, InChI or InChIKey are removed (a quoted InChI was taken for a SMILES and replaced the real one); unusable peaks (zero or negative intensity or m/z) are removed when the file is read, before the SPLASH is computed, so that the same spectrum gets the same SPLASH whatever the format (GNPS JSON keeps zero-intensity peaks that its MSP and MGF exports leave out) and is recognized as a duplicate; quotes around JSON values are removed, as in MSP; the instrument is also searched in the ionization / ion source fields and in other fields that describe it (MoNA `mass analyzer`, `chromatography type`, `sample introduction`; GNPS JSON `Ion_Source`), so that GNPS JSON gives `LC-ESI-FT` like its MSP export instead of `LC-FT`; a collision energy written in the name is kept in `COLLISIONENERGY` when that field is empty, for every format (GNPS, MS-DIAL `CE30`); MoNA JSON spectra without the `In-Silico` tag go through the same in silico detection as the other formats (they were always marked experimental, even with an `in-silico QTOF` instrument type); MoNA `origin`, tags and library, and library identifiers (MoNA MSP `LipidBlast2022_006705`) are used to recognize in silico spectra, with a version number allowed after a tool name; a MSP precursor m/z equal to a value computed by MoNA (`computed [2M-H]-=…`) is used only when the measured one (`pepmass`) is missing; the original ionization (`LC-ESI`) is kept for the instrument search, which only saw the normalized one (`ESI`) and lost the LC (GNPS JSON gave `ESI-FT`, its MSP `LC-ESI-FT`); spaces around MoNA JSON field names are removed, as in MSP (`analytical method     ` was not read), and MoNA `analytical method` (`Theoretical in-silico spectrum (QCEIMS)`) is used to recognize in silico spectra, as are the other names of a MoNA JSON compound (`$:07 In-Silico-Spectrum`, written as `Synon:` lines in MoNA MSP); in MoNA MSP, the original exact mass of the Comments (`exact mass=`) is used before the `ExactMass:` line, computed by MoNA; decimal numbers of the comments are ignored when the instrument is searched there (computed masses such as `365.5269` gave `AB SCIEX 365`, `LC-QQQ` to spectra without any instrument information), and a comment made of `"key=value"` fields (MoNA MSP), already read field by field, is no longer searched for the instrument (single letters gave `B`, `FD` or `CE`); a SMILES, InChI or InChIKey found in the wrong field is moved only when it really has the expected form (checked SMILES atoms, complete InChI, InChIKey) and when the right field is empty, so it never overwrites a value of the file; the adduct written at the end of a name emptied as a placeholder (GNPS MGF `0 [M-H]-`) is still read, and an adduct written after a structure (`InChI=1S/… [M-H]-`) is removed from it and used when no adduct is found elsewhere (an adduct written in full between brackets, such as `[M]-`, is accepted there even when it is not in the adduct tables, as in the adduct field); GNPS "suspect" spectra (`Suspect related to …`, structure followed by a mass offset such as `- 14.016 Da`), whose structure is that of a related compound and not of the measured molecule, are deleted (`suspect_related_structure.csv`, counted with the spectra without usable structure) (a damaged MoNA InChIKey `ZZORFUFYDOWNEF-UHFFFAOYAR` replaced the SMILES), and a value shaped like an InChIKey is preferred to one that is not (GNPS JSON `INCHI_AUX`, an InChI followed by the adduct, removed about 350 spectra that have a structure); ClassyFire and NPClassifier classes taken from the internal database are written without the double quotes that the categorical columns added (`"Alkaloids"`, `"NOT FOUND"`); spectra without peaks are no longer dropped silently while reading: they are written to `DELETED_SPECTRUMS` with the reason `peaks list is empty`; new MoNA field names read: `MSn observed RT` (retention time), `ionization method`, `fragmentation mode` / `fragmentation method` / `collisiontype` (fragmentation method), `mstype` (MS level), `monoisotopic mass`, `spectrum analyzer type` (used for the instrument search); the ionization written in the ion mode field (MoNA `ionization mode: ESI`) is read when no other field gives it; a MoNA JSON comment written as a list of `"key=value"` fields (`"retention time=2.2957"`) is read field by field, as in MSP, and used only when no real field gives the value.
  - **Collision energy**: read when written at the end of the name with its unit (GNPS / Metaboanalyst `TYRAMINE - 20.0 eV`, `… 20eV M-H`, `Asperterrol(10-30V+20V)`, `… 40 NCE`; the energy is removed from the name, an adduct after it is kept), as an MS-DIAL name piece with a space or a unit (`CE 20V`, `30eV`, also in the middle of the name; `CE0` is kept as written, `CE0`, since `0` alone means an empty value), and in the comment when the field is empty (MassBank `averaging of repeated ion fragments at 30.0 NCE`, `CollisionEnergy:102040`, `CE:Ramp 5-60 V`, `collisionenergy=90`), never for GC / EI spectra (70 eV is the ionization energy); new MoNA field names read: `collision energy voltage`, `collision energy level`, `stepped nce`, `hcd`, `collision energies`; a collision energy with a number wins over a level written in words (`high`).
  - **Collision energy written the same way everywhere**, without any unit conversion: the unit is kept (`eV`, `V`), percentages, `NCE` and `(nominal)` are written `NCE` (`75 % (nominal)` -> `75 NCE`), useless decimals are removed (`20.0eV` -> `20 eV`), several energies are separated by `/` and preceded by `Ramp` or `Stepped` only when the source says so or the writing makes it clear (`Ramp 5-60 V` -> `Ramp 5/60 V`, `20-40eV` -> `Ramp 20/40 eV`, `HCD (NCE 20-30-40%)` -> `Stepped 20/30/40 NCE`), otherwise as a plain list (`[20.0, 30.0, 60.0]` -> `20/30/60`, GNPS `102040` -> `10/20/40`); a fragmentation method written with the energy (`35 CID`, `65HCD`) goes to `FRAGMENTATIONMETHODE` when that field is empty; an analyzer written after the energy (`35 eV FT-MS`, `35 eV IT-MS`) is removed from it and written in `INSTRUMENTTYPE` only when that field is empty (never overwritten); other writings (`CE0`, `low`, `3 kV`, `15, 30, 45, 60, 70 or 90 (nominal)`...) are kept as they are; `CE75` -> `75`, `NCE_20_30_40` -> `20/30/40 NCE`.
  - **Lower memory use, same results**: the peaks are no longer kept twice (a text copy of every peak list was stored next to the peaks, used only by some deletion files: it is now written from the peaks when needed); the spectra deleted during cleaning are written to `DELETED_SPECTRUMS` and freed batch by batch instead of being kept until the end of the step; the MSP text is produced while writing instead of being prepared for all spectra in advance (the "Converting CSV to MSP" step disappears); the mass & adduct correction and the splitting into output files move the spectra instead of copying them; unused reserved memory is released after reading the files and after cleaning; the raw text of the MSP and MGF files is freed batch by batch while it is read. On the full test set (35 files, 9.3 GB), the memory peak drops from 29.9 GB to 20.2 GB (-33 %), with byte-identical outputs and the same run time; reading GNPS MSP alone needs 22 % less memory.
  - **Stop button and Ctrl+C stop a run within about a second, safely**: a stop flag shared by all threads is checked in every long loop (reading, cleaning, RDKit, correction, duplicates, writing...), instead of only between steps; Ctrl+C is caught by the Rust engine in the command line (a second Ctrl+C quits immediately). When a run stops or fails, the output directory is put back exactly as it was before the run: files created by the run are removed, completed files are cut back to their previous content, replaced files and the previous outputs set aside by `reset_updates` are restored (they were deleted at the start of the run before).
  - **De novo formulas of negative spectra written with `-`** (`C7H4NO3-/1.23`): the ion is deprotonated (one H removed), but `+` was always written.
  - **GC spectra without ion mode** are still set to positive (electron ionization), except in negative chemical ionization (NCI, ECNI...), where nothing is guessed.
  - **mzSpecLib output rewritten**: the spectra are sent by the Rust engine, in batches, straight to the `mzspeclib` library (no more reading back of the MSP files, so `--msp no` no longer prevents the mzSpecLib output), converted in parallel. Every FragHub field is written separately with its PSI-MS term (adduct, charge read from the adduct, ms level, dissociation method, ionization type, scan polarity, collision energy in eV or normalized collision energy in %, ramps, retention time in minutes, origin observed / predicted, splash key, masses...) or, when the vocabulary has no suitable term, as a named free attribute (`SPECTRUMID`, `FILENAME`, `INSTRUMENT`...); empty and `NOT FOUND` values are no longer written; each file starts with a library header (format version, name). Before, the generic MSP reader of `mzspeclib` lost most fields, wrote every collision energy in eV (`35 V` became 35 eV) and dropped spectra with a text retention time or an unknown ion mode. Checked with the `mzspeclib` validator.
  - **Fragmentation method** read when it is written elsewhere and `FRAGMENTATIONMETHODE` is empty: an isolated upper-case abbreviation (HCD, CID, EAD, UVPD, ETD...) in the instrument or its type (GNPS `HCD; Lumos`, `LC-ESI-CID`), in the origin or the library (MS-DIAL `origin=HCD natural product library`, MoNA `UVPD on Thermo IQX`), `in source CID` -> `in-source CID`, and a method stuck to an energy in a GNPS name (`Catechin_HCD40_170906`: HCD, and 40 as energy if empty); the origin written in the comment is read too (MS-DIAL `origin=…`, MoNA MSP `"origin=uvpd.msp"`); never a PubChem identifier (`CID 638`); when two different methods are written, only the one that begins a library or file name is taken, if it is the only one (`HCD natural product library, acquired in adjunct with UVPD library` -> HCD); methods written in lower case are written in upper case (`cid` -> `CID`), other method writings are kept (`LOW-ENERGY CID`), and a value that is not a method is removed (MoNA NIST-Glycan `IT/ion trap`, an analyzer).
  - **Duplicates**: the duplicate kept (same SPLASH and InChIKey) gets the values of the removed duplicates for its empty fields (retention time, collision energy, instrument...); no value of the kept spectrum is replaced, and its file, database, identifiers, comment and in silico status stay its own. Before, the information of the removed duplicates was lost (Metaboanalyst NEG: 283 retention times and 61 collision energies out of 2,744 duplicates).
  - **Molecule normalization**: InChI and InChIKey are computed on the desalted, neutralized molecule, before the tautomer step (standard identifiers, stereochemistry no longer lost); output SMILES are normalized with the RDKit canonical tautomer (stereochemistry kept), unless it changes the InChI; salts written as InChI are now desalted too. The internal database is re-normalized the same way (`fraghub_rust.renormalize_internal_database`); very big molecules (more than 100 heavy atoms, `FRAGHUB_RENORM_BIG_ATOMS`) are computed last, so that a few molecules taking hours no longer hold up the rest of the database.
  - **Instrument tree regenerated** (`datas/instruments_tree.json`, built from `Instrument_tree.xlsx` by the new Rust tool of the `instrument_decision_tree` branch, which replaces the pandas script): the keys are written like the text FragHub searches, so 11 models that could never be found are now recognized (TripleTOF `6600`/`5600`, `5500+`, `6500+`, `PTR-TOF …`, `JMS-HX/HX 110A`); with a known model, LC/GC is also completed when the ionization is known (`ESI-FT` -> `LC-ESI-FT`; micrOTOF-Q: ESI -> LC, APCI -> GC), so GC spectra written `CI-B` are now recognized as GC; models are sorted by length over the whole tree (without a brand, `Esquire 3000` was taken for the AB SCIEX `3000`); where the spreadsheet gives both HIGH and LOW, the resolution is the majority of its instruments when the analyzer is known (QTOF -> HIGH, QQQ / QQ / QIT -> LOW) and is no longer completed without an analyzer (`ESI`, `GC`, `EI` or a brand alone got HIGH); unused branches removed (10 277 -> 5 090 solutions).
  - **Instrument search when several brands are cited** (pump, column or chromatograph of another brand): the brand whose model is found wins, otherwise the one that recognizes the most levels (LC/GC, analyzer, ionization); before, the first brand of the tree always won and the instrument stayed unknown (`LC-10ADVPmicro HPLC, Shimadzu; LTQ Orbitrap, Thermo Scientific` -> Shimadzu; now Thermo LTQ Orbitrap, high resolution). Unchanged when a single brand is cited.
  - **LC/GC completed in the instrument type**: when the type kept has no LC, GC or CE, the ionization decides (ESI -> LC, it is never done in GC; EI -> GC), otherwise the LC/GC of the recognized model (`ESI-QTOF` -> `LC-ESI-QTOF`, `EI-B` -> `GC-EI-B`, `APCI-ITFT` of a known model -> `LC-APCI-ITFT`). Before, the type of the file was kept without its separation when the tree proposed a less precise type (`ESI-QTOF` of a TripleTOF 5600, typed `TOF` in the spreadsheet).
  - **Direct injection (DI) libraries**: spectra acquired without chromatography (word `DI` in the type or the ionization, `Flow-injection`, `direct infusion`, `FIA` in the instrument fields, or an explicit sentence in the comment such as MassBank's `The sample was injected by direct infusion.`) get `DI` instead of `LC` in their type (`DI-ESI-QTOF`) and are written in new `POS_DI` / `NEG_DI` files (and their in silico versions) in CSV, MSP, JSON and mzSpecLib, with their own branch in the report. PTR instruments are DI in the instrument tree. Apart from the output files, DI spectra follow the LC rules (adduct required).
  - **`QQ` searched as `QQQ` in the instrument tree** (MassBank writes triple quadrupoles `QQ`, the tree `QQQ`): the resolution of these spectra is found again; the type written in the file is not changed.
  - **Instrument tree regenerated from the corrected spreadsheet**: TripleTOF -> QTOF; Q Exactive, Exploris -> QFT; Exactive -> FT; LTQ -> IT; triple quadrupoles written `QQQ` everywhere; ZQ -> Q, ESI, LOW; TSQ ionization ESI (not EI); unit-resolution analyzers (triple quadrupoles, ion traps) LOW; chromatographs removed (Waters 2690, Thermo Trace 1310); typos; multi-word models recognized in any word order (`TripleTOF 6600` and `6600 TripleTOF`).
